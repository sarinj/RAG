19. EVENT-DRIVEN ARCHITECTURE
======================================================================

HCA uses event-driven patterns for several high-volume systems.

For critical workflows, event production should be durable.

The preferred approach for database-backed services is the transactional outbox pattern.

In the transactional outbox pattern:
1. the business state change and outbox event are written in the same database transaction;
2. the transaction commits;
3. a worker or change-data-capture process publishes the event;
4. downstream consumers process the event;
5. consumers use idempotency or deduplication where necessary.

Redis notifications may be used as a wake-up optimization.

Redis must not be treated as the sole source of truth for guaranteed event delivery.

Failed messages may be retried with exponential backoff.

Messages that exceed the configured retry policy are moved to a dead-letter queue or dead-letter topic.

44. LANTERN RETRIEVAL BEHAVIOR
======================================================================

Dense retrieval is especially useful when user wording differs from document wording.

BM25 is useful for exact terms, identifiers, policy codes, unusual names, and specific error messages.

Hybrid retrieval combines both signals.

The current production configuration weights dense retrieval at 0.65 and BM25 at 0.35 before reranking.

These weights are not considered universally optimal.

The team periodically tunes retrieval weights using the evaluation set.

For some exact-code troubleshooting queries, BM25 contributes more useful candidates than dense retrieval.

======================================================================
45. LANTERN HALLUCINATION POLICY
======================================================================

Lantern should not invent missing information.

If authoritative sources do not contain enough information, the assistant should say so.

The assistant may explain what information was found and what information is missing.

The assistant should not infer a person's salary from their role.

The assistant should not infer the technology used by a project merely because that technology is common elsewhere in HCA.

The assistant should distinguish between citywide defaults and project-specific facts.

For example, PostgreSQL is the default relational database for new HCA systems, but that does not prove that every named project uses PostgreSQL.

======================================================================
46. DOCUMENT AUTHORITY RULES
======================================================================

Not every document has equal authority.

For policy questions, the preferred order is:
1. current approved policy;
2. current approved standard;
3. current operational procedure;
4. current guidance;
5. archived material.

Draft documents should not override approved policies.

If two approved sources conflict, the system should surface the conflict rather than silently selecting one unless a precedence rule exists.

A newer document is not automatically more authoritative if it is still a draft.

======================================================================
47. MODEL HOSTING
======================================================================

HCA hosts some open-source models internally.

Internal models are served on GPU clusters in DC-EAST.

The inference platform supports batching, KV-cache reuse, and quantized models.

The platform team uses vLLM for several internal model-serving workloads.

Not every AI application uses vLLM.

Some specialized models are served using custom inference services.

GPU scheduling is handled through Kubernetes-based infrastructure.

The largest internal shared inference cluster currently contains 96 GPUs.

A future expansion to 192 GPUs has been approved but is not yet operational.

======================================================================
48. EMBEDDING PLATFORM
======================================================================

HCA maintains an internal embedding service.

The service supports multiple embedding models.

The standard English retrieval model currently produces 1,024-dimensional embeddings.

A multilingual model produces 768-dimensional embeddings.

Embeddings are normalized before storage for most semantic-search applications.

Cosine similarity is the default similarity metric for normalized embeddings.

Some experimental systems use dot product.

The embedding platform records model version in vector metadata.

Re-indexing is required when a new embedding model changes vector dimensionality.

======================================================================
49. VECTOR DATABASES
======================================================================

HCA uses more than one vector-search technology.

Lantern's production index uses a managed vector-search cluster built on an HNSW-based approximate nearest-neighbor index.

A separate research environment uses PostgreSQL with a vector extension for smaller experiments.

The existence of a standard vector platform does not prohibit teams from using another approved technology when justified.

Vector indexes must store enough metadata to enforce access controls during retrieval.

Post-filtering alone is not acceptable for highly sensitive datasets if unauthorized chunks could already have been retrieved into the application process.

======================================================================
50. QUERY REWRITING
======================================================================

Lantern may rewrite user queries before retrieval.

Query rewriting is used to:
- expand abbreviations;
- resolve known internal acronyms;
- add missing domain context;
- generate alternative retrieval queries.

The original user query is retained.

Rewritten queries must not add unsupported factual assumptions.

For example, a query asking "Who owns Atlas?" should not be rewritten to assume which Atlas project the user means when multiple projects named Atlas exist.

======================================================================
51. RERANKING
======================================================================

Lantern uses a cross-encoder reranker after initial retrieval.

The reranker scores the query together with each candidate chunk.

The reranker is slower than embedding similarity but more accurate for many relevance judgments.

Therefore it is applied to a smaller candidate set rather than the entire corpus.

The production system reranks 30 candidates and keeps 8.

Latency budgets may require smaller candidate sets for interactive applications.

======================================================================
52. PROMPT CONSTRUCTION
======================================================================

Retrieved chunks are assembled into a context package.

The context package includes:
- source title;
- section heading;
- document status;
- publication date;
- chunk text;
- access classification.

Chunks from higher-authority sources may be ordered before lower-authority sources.

Very similar duplicate chunks may be deduplicated.

The final prompt instructs the model to rely on retrieved evidence and identify uncertainty.

======================================================================
53. CITATION REQUIREMENTS
======================================================================

For policy-sensitive answers, Lantern should cite the source document and section.

Citations should support the specific claim they follow.

A citation to an unrelated section is considered a citation error even if the overall document is relevant.

Multi-claim answers may require multiple citations.

If a statement is based on inference rather than explicit text, the answer should make that distinction clear.

======================================================================
54. SEARCH ANALYTICS
======================================================================

Lantern records anonymized retrieval analytics.

Metrics include:
- query count;
- retrieval latency;
- reranking latency;
- no-answer rate;
- most frequently retrieved sources;
- user feedback;
- abandoned searches.

Raw query logs containing potentially sensitive information have restricted access.

Analytics data is retained for 180 days in identifiable form and then aggregated for longer-term trend analysis.

55. HR LEAVE POLICY
======================================================================

Full-time HCA employees receive 22 days of annual leave per calendar year.

Employees with at least 7 completed years of service receive 27 days.

Employees with at least 15 completed years of service receive 30 days.

A maximum of 7 unused annual-leave days may be carried into the next calendar year.

Carried-over days must normally be used by April 30.

Unused carry-over beyond that date expires unless an approved exception applies.

Parental leave is governed by a separate policy.

Medical leave is not deducted from annual leave when supported by required documentation.

56. REMOTE WORK POLICY
======================================================================

Eligible office-based employees may work remotely up to three days per week with manager approval.

Some roles are designated on-site due to operational requirements.

Employees working remotely must remain reachable during agreed working hours.

HCA may require in-person attendance for training, incident response, planning sessions, or operational needs.

Employees working permanently outside the metropolitan region require additional HR and tax review.

Remote work is not an entitlement for every position.

======================================================================
57. TRAVEL EXPENSE POLICY
======================================================================

Employees traveling for approved work may claim reasonable transportation, lodging, and meal expenses.

Air travel under six hours should normally be booked in economy class.

Premium economy may be approved for flights longer than six hours.

Business class requires executive approval except where required by medical accommodation or exceptional circumstances.

Hotel expenses should remain within published city limits unless no compliant accommodation is available.

Receipts are required for individual expenses above 25 Helios Credits.

HCA uses four information classifications:
- Public
- Internal
- Confidential
- Restricted

Public information may be disclosed openly.

Classification labels should follow the data through approved systems.

======================================================================

Employees should not send Restricted information through ordinary unencrypted email.

Confidential information may be sent using approved secure messaging mechanisms.

Business records created in messaging platforms may still be subject to retention and records-management requirements.

Sensitive discussions should use approved systems.

======================================================================
60. DEVICE MANAGEMENT
======================================================================

HCA-issued laptops are centrally managed.

Full-disk encryption is mandatory.

Endpoint protection must remain enabled.

Users must not disable security software without authorization.

Lost or stolen devices must be reported immediately.

Mobile devices used for HCA email must meet minimum security requirements.

Rooted or jailbroken devices are not permitted to access managed HCA mobile services.

======================================================================
61. PHYSICAL ACCESS
======================================================================

Access badges are required in controlled HCA facilities.

Employees must not lend badges to other people.

Visitors must be escorted in restricted areas unless specifically authorized.

Data-center access requires separate authorization.

DC-EAST requires two-factor physical access for high-security zones using a badge plus biometric verification.

Tailgating through secure doors is prohibited.

======================================================================
62. FACILITY INCIDENTS
======================================================================

A facility incident may involve:
- fire;
- flooding;
- power loss;
- HVAC failure;
- physical security breach;
- structural damage.

======================================================================
63. GENERATOR AND UPS SYSTEMS
======================================================================

Primary data centers use UPS systems to bridge short power interruptions.

Backup generators provide longer-duration support.

DC-EAST maintains fuel reserves intended to support at least 48 hours of generator operation at planned emergency load.

Quarterly generator tests are performed under load.

======================================================================
64. COOLING AT DC-EAST
======================================================================

DC-EAST uses a combination of air cooling and liquid cooling.

General-purpose racks primarily use air cooling.

High-density AI racks may use direct-to-chip liquid cooling.

The facility is designed with redundant cooling loops.

Cooling alarms are integrated into the operations monitoring platform.

A high coolant temperature alarm does not automatically shut down all servers.

Operators evaluate severity and may migrate workloads before initiating shutdown procedures.

======================================================================
65. CAPACITY MANAGEMENT
======================================================================

Infrastructure teams review compute, storage, network, and power capacity monthly.

Capacity forecasts cover at least 18 months for critical shared platforms.

Projects expected to require more than 500 kilowatts of new data-center power must be reviewed by the Capacity Council.

The 2026 AI expansion is the main driver of new DC-EAST power demand.

No plan has been approved to build a fourth primary data center before 2028.

======================================================================
66. FINANCIAL SYSTEMS
======================================================================

HCA's core finance platform handles budgeting, procurement, accounts payable, payroll integration, and financial reporting.

Financial posting periods are closed monthly.

Certain corrections require approval from both finance and the originating department.

Financial transaction records are retained for at least seven years.

Production financial data is classified as Confidential unless a more restrictive classification applies.

======================================================================
67. PAYMENT PROCESSING
======================================================================

The Citizen Services Portal supports online payments for selected services.

Payment-card processing is outsourced to approved payment providers.

HCA systems use tokens rather than storing full payment-card numbers.

Refunds generally return to the original payment method.

Refund timing depends on the payment provider and financial institution.

Duplicate payment prevention uses idempotency keys for supported transaction flows.

======================================================================
68. PARKING SERVICES
======================================================================

HCA manages municipal parking permits and selected on-street parking systems.

Residents may apply for residential parking permits online.

A standard residential parking permit is valid for one year.

Digital permits are associated with vehicle license plates.

Temporary visitor permits may be issued for shorter durations.

Parking enforcement officers verify permit status using mobile devices.

======================================================================
69. PROJECT VECTOR
======================================================================

Project Vector is a parking-analytics initiative.

It began in June 2026.

The project is led by Noor Al-Khatib.

Vector analyzes anonymized parking occupancy data to improve parking policy and enforcement planning.

The first pilot includes 12,000 parking spaces.

The project explicitly excludes facial recognition.

License-plate data used for enforcement is governed separately from anonymized occupancy analytics.

======================================================================
70. BUILDING MANAGEMENT SYSTEMS
======================================================================

HCA operates building-management systems across major municipal facilities.

These systems monitor HVAC, lighting, access systems, elevators, and selected environmental conditions.

Building-management networks are segmented from normal office networks.

Remote vendor access is permitted only through approved gateways.

Default vendor passwords must be changed before production deployment.

Critical configuration backups are stored securely.

======================================================================
71. FIRE SAFETY SYSTEMS
======================================================================

Fire alarm systems are treated as life-safety systems.

They must not be disabled for routine energy optimization.

Maintenance that requires temporary impairment must follow approved fire-watch procedures.

Fire alarm events have higher operational priority than comfort-related building alarms.

======================================================================
72. ENVIRONMENTAL SENSORS
======================================================================

HCA operates environmental sensors for air quality, noise, temperature, rainfall, river levels, and selected pollutants.

Low-bandwidth sensors often use LoRaWAN.

Air-quality stations report particulate matter including PM2.5 and PM10.

Rainfall data is used by flood-response models.

Sensors may be temporarily marked unreliable if calibration checks fail.

Unreliable data should not be silently treated as accurate.

======================================================================
73. FLOOD MONITORING
======================================================================

Helios City has 126 automated flood-monitoring stations.

River-level sensors update every 2 minutes during normal conditions.

During severe weather, selected stations update every 30 seconds.

Flood warning thresholds vary by location.

A high sensor reading does not automatically mean evacuation is required.

Emergency managers consider rainfall forecasts, upstream conditions, tide levels, and infrastructure status.

======================================================================
74. PROJECT RIVERGUARD
======================================================================

Project RiverGuard improves flood prediction.

It began in 2024 and is led by Mei Tan.

The model combines:
- rainfall radar;
- river gauges;
- tide forecasts;
- soil saturation;
- drainage capacity.

The project produces forecasts up to six hours ahead.

In 2025 testing, RiverGuard improved warning lead time by an average of 22 minutes compared with the previous rules-based method.

RiverGuard recommendations are advisory.

Emergency officials remain responsible for issuing evacuation orders.

======================================================================
75. AIR QUALITY PROGRAM
======================================================================

The city publishes an hourly air-quality index.

The index is derived from multiple pollutants.

PM2.5 is often the dominant pollutant during dry-season haze events.

When air quality reaches the severe category, HCA may recommend reducing strenuous outdoor activity.

School closures are decided by the Education Department, not automatically by the air-quality system.

======================================================================
76. LIBRARY SYSTEM
======================================================================

The municipal library network contains 64 branches.

Residents may borrow physical books for 21 days.

Most books can be renewed twice if no other user has placed a hold.

E-books have separate lending rules determined by licensing agreements.

Lost physical items may incur replacement charges.

Children under 16 may obtain library cards with guardian approval.

======================================================================
77. DIGITAL ARCHIVES
======================================================================

HCA maintains a digital archive for historical municipal records.

Archived records may include photographs, maps, council documents, planning records, and selected audiovisual material.

Not all archived material is publicly accessible.

Privacy, copyright, security, and preservation restrictions may apply.

Digitized items preserve metadata describing provenance and rights status.

======================================================================
78. OPEN DATA PORTAL
======================================================================

The Helios Open Data Portal publishes more than 600 datasets.

Common topics include:
- transit;
- environment;
- budgets;
- public facilities;
- street maintenance;
- planning;
- demographics.

Datasets are assigned owners and update frequencies.

Some datasets update in near real time.

Others update monthly, quarterly, or annually.

The portal does not publish data that would create unacceptable privacy or security risk.

======================================================================
79. DATA QUALITY
======================================================================

Dataset owners are responsible for data quality.

Common dimensions include:
- completeness;
- accuracy;
- timeliness;
- consistency;
- uniqueness.

A dataset may be complete but inaccurate.

A dataset may be accurate but stale.

Critical analytical datasets should document quality checks.

Known limitations should be published when they materially affect interpretation.

======================================================================
80. DATA CATALOG
======================================================================

The internal data catalog records:
- dataset name;
- owner;
- description;
- classification;
- source system;
- refresh schedule;
- retention policy;
- access procedure.

Catalog registration is mandatory for new enterprise datasets classified Confidential or Restricted.

The catalog does not store every dataset's full contents.

======================================================================
81. DATA SHARING
======================================================================

Internal data sharing should follow least-privilege principles.

Cross-department access may require approval from the dataset owner.

Restricted datasets may require privacy, legal, or security review.

Bulk exports of sensitive data should be minimized.

Where practical, teams should provide filtered APIs or governed analytical views instead of unrestricted raw copies.

======================================================================
82. ANALYTICS PLATFORM
======================================================================

HCA operates a central analytics platform.

It supports SQL analytics, notebooks, dashboards, and scheduled data pipelines.

Production analytical jobs should use managed service identities.

Shared credentials are discouraged.

Heavy queries should be optimized to avoid unnecessary resource consumption.

Long-running exploratory workloads may be moved to dedicated compute pools.

======================================================================
83. MACHINE LEARNING OPERATIONS
======================================================================

Machine-learning models deployed in production must have documented owners.

High-impact models require documented evaluation datasets and monitoring.

Model performance can degrade when real-world data changes.

Teams should monitor drift where relevant.

Retraining schedules should be based on model needs rather than arbitrary fixed intervals.

Model version and training-data lineage should be recorded.

======================================================================
84. BIAS AND FAIRNESS REVIEW
======================================================================

High-risk AI applications require fairness review.

Fairness review considers whether performance differs materially across relevant groups.

A fairness metric must be chosen based on context.

There is no single fairness metric that is correct for every application.

Observed differences require investigation, not automatic assumptions about cause.

Decisions to deploy high-risk AI must include human accountability.

======================================================================
85. HUMAN OVERSIGHT
======================================================================

Human oversight must be meaningful.

A human reviewer should have enough information and authority to challenge or override an automated recommendation.

Merely placing a person in the workflow does not automatically create effective oversight.

High-risk systems should provide reason codes or supporting evidence when feasible.

======================================================================
86. MODEL MONITORING
======================================================================

Production model monitoring may include:
- input drift;
- output distribution changes;
- prediction confidence;
- error rates;
- latency;
- resource consumption;
- fairness indicators.

Not every metric is relevant for every model.

Alerts should focus on changes that may indicate meaningful degradation.

======================================================================
87. PUBLIC AI DISCLOSURE
======================================================================

When residents interact directly with a generative AI assistant on an HCA public service, the interface should disclose that the user is interacting with an AI system.

The disclosure should not imply that the AI has authority it does not have.

For regulated decisions, final authority remains with designated human officials unless law and policy explicitly provide otherwise.

======================================================================
88. SECURITY AWARENESS TRAINING
======================================================================

All employees must complete annual security awareness training.

New employees must complete baseline training within 30 days of starting work.

Phishing simulations are conducted periodically.

Employees are encouraged to report suspicious messages.

Repeated failure to complete mandatory training may result in account restrictions.

======================================================================
89. PHISHING RESPONSE
======================================================================

Employees who suspect they clicked a phishing link should report it immediately.

They should not wait to see whether unusual activity occurs.

If credentials were entered, the user should change the password and notify the security team.

Security staff may invalidate active sessions and tokens.

Rapid reporting can reduce the impact of credential theft.

======================================================================
90. INCIDENT COMMUNICATION
======================================================================

Major incidents require coordinated internal and external communication.

Technical teams should avoid publishing unverified root-cause claims during an active incident.

Initial updates should focus on known impact, affected services, user actions, and investigation status.

Root cause may be published after sufficient evidence is available.

======================================================================
91. POSTMORTEMS
======================================================================

HCA uses blameless postmortems for major operational incidents.

A blameless postmortem focuses on system conditions, contributing factors, decisions, and improvements rather than personal blame.

Postmortems should include:
- timeline;
- impact;
- detection;
- response;
- contributing factors;
- corrective actions.

Corrective actions should have owners and target dates.

======================================================================
92. ON-CALL PRACTICES
======================================================================

Tier 1 services require 24-hour on-call coverage.

On-call rotations should be large enough to avoid chronic overload.

Escalation paths must be documented.

Pages should be reserved for issues requiring timely human action.

Non-urgent notifications should use lower-priority channels.

======================================================================
93. MAINTENANCE WINDOWS
======================================================================

Standard maintenance windows vary by service.

Citizen-facing systems generally schedule planned maintenance between 01:00 and 05:00 local time when possible.

Transit operations systems may use different windows because transport runs during late-night hours.

Emergency services must maintain continuity even during maintenance.

Planned downtime should be communicated in advance when users are affected.

======================================================================
94. RELEASE MANAGEMENT
======================================================================

High-risk releases may use canary deployment.

Canary deployment sends a small percentage of production traffic to the new version before wider rollout.

Rollback criteria should be defined in advance.

A canary that shows increased error rates or unacceptable latency should not automatically continue rollout.

Feature flags may be used to separate code deployment from feature activation.

======================================================================
95. DATABASE MIGRATIONS
======================================================================

Database migrations should be designed to minimize downtime.

Large schema changes should avoid long-running locks.

Backward-compatible migrations are preferred.

Applications may use expand-and-contract techniques for complex changes.

Destructive migration steps should be delayed until old application versions are no longer active.

======================================================================
96. CACHE USAGE
======================================================================

Caches may reduce latency and backend load.

Cached data must have appropriate expiration or invalidation behavior.

Critical authorization decisions should not rely on indefinitely stale cache entries.

Cache failures should not corrupt source-of-truth data.

Some applications may operate with degraded performance when Redis is unavailable.

Others may temporarily disable features that depend heavily on cache state.

======================================================================
97. RATE LIMITING
======================================================================

Public APIs use rate limiting to protect service reliability.

Rate limits may vary by API and client class.

Authenticated partners may receive higher limits than anonymous users.

Rate-limit responses should include clear retry guidance where possible.

Clients should use exponential backoff rather than aggressive immediate retry loops.

======================================================================
98. MESSAGE RETRIES
======================================================================

Distributed systems should assume that message delivery may be duplicated.

Consumers should be idempotent where duplicate processing could cause harm.

Retries should use backoff.

Infinite immediate retries are prohibited.

Poison messages should eventually move to dead-letter handling.

Operators should have tools to inspect and replay dead-lettered messages safely.

======================================================================

RAG systems must consider time.

153. RAG EVALUATION NOTES
======================================================================

This corpus intentionally contains several traps.

Trap A: Global defaults versus project-specific facts.
Example: PostgreSQL is the default relational database for new systems, but this does not prove that Project Solaris, Orbit, Aqua, RiverGuard, or Lantern use PostgreSQL internally.

Trap B: Similar names.
Project Atlas is explicitly defined as an infrastructure-dependency mapping program. A retrieval system should avoid confusing it with other hypothetical Atlas projects.

Trap C: Historical versus current policy.
The archived 2024 remote-work guide allowed two remote days, while the approved 2026 policy allows up to three days. Retrieval quality must consider effective date and document authority.

Trap D: Human oversight.
The document explicitly says that simply inserting a human into a workflow does not automatically create meaningful oversight.

Trap E: Measurements versus guarantees.
Emergency response targets, availability targets, and timing objectives are goals, not universal guarantees.

Trap F: Advisory systems versus final authority.
RiverGuard provides forecasts, but emergency officials decide evacuation orders.

Trap G: Correlation versus fact.
A high fraud score does not mean fraud definitely occurred.

Trap H: Retrieval versus authorization.
A search system may technically find a document, but the user may still lack permission to view it.

Trap I: Caching versus source of truth.
Redis may accelerate systems, but business-critical state must not depend on transient cache state alone.

Trap J: "Newest" does not always mean "authoritative."
A draft document written yesterday should not automatically override an approved policy issued last year.
